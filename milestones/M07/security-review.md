# security-reviewer on the M07 infra/IAM/workflow diff — findings and disposition

Run 2026-08-21 against `git diff main...m07-governance`. One HIGH (merge-
blocking), four MEDIUM, four LOW. **The HIGH was introduced by this branch.**

Recorded in full rather than summarised, because two findings were defects in
code I had just written and one of them was in the control the whole register
rests on.

## The reviewer's answers to the five questions I asked

- **Fork PRs once the flag flips:** no credential assumption, no Bedrock spend, no disclosure beyond what is already public. `unit` runs fork-authored code with `contents: read`, no role, no secrets — unchanged by this diff. `golden-set` would have failed closed correctly at `configure-aws-credentials` with an empty `EVAL_RC`, confirming the M04/M05 hardening. The problem was operational, not a breach: see M3. **Two things to verify outside the diff:** that Settings → Actions requires approval for fork-PR workflows at least at the default, given `unit` executes contributor code; and that for `pull_request` the workflow file comes from the PR head, so a fork can edit `evals.yml` — the ceiling is unchanged because there is nothing for it to reach, but the file is not a control against a fork.
- **`sub`/`aud` scoping:** correct, and it has a property I did not claim and get for free — `pull_request_target`, the dangerous sibling that *does* receive secrets and a write token, carries `sub: …:ref:refs/heads/main` and is excluded by the pin. Incomplete only in the two ways above.
- **Is `dynamodb:Scan` all it needs:** yes, traced end to end. Base table only, no index. Three related notes now on file: `emit_pass_rate` is defined and **never called**, so no `cloudwatch:PutMetricData` grant — do not add one if someone wires it up silently; `resolve_api_url`'s CloudFormation fallback is ungranted and fails closed, but its visible error reads "No API URL", not "STAGING_API_URL is unset"; and the registry table uses the default AWS-owned key, so a move to a CMK would break this role with an opaque `AccessDenied`.
- **`pyyaml==6.0.3` and `unit`:** clean. The one behavioural change is that `tests/test_ci_eval_role.py` now synthesizes the full core stack in `unit` — offline, explicit environment, no context lookups, no credentials.
- **Injection surface:** nothing in this diff creates a new path from fetched Federal Register / eCFR text into a prompt. The register reads local files only and its text is printed, never sent to a model. L4 is a rendering concern, not tool-steering.

## The gap worth carrying forward

The reviewer's sharpest structural point, in its own words: live-IAM sufficiency
for the role is unproven until the first run, and **that first run is currently
scheduled to be a public PR on a repo where the gate is not required** — so an
`AccessDenied` would surface as a red advisory check rather than as something
anyone must act on. Phase 2.5 (adding `golden-set` to required checks) is what
changes that, and it should land before or with the first live run rather than
after.
